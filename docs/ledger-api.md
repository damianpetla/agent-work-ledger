# Ledger service contract v1 — DAM-32

**Tech Lead · gpt-6.1-sol · medium (configured)**

This is the implementation contract, not evidence of an implemented service. Producer [event formatVersion 1](event-contract.md) remains unchanged. `serviceVersion: 1`, SQLite `user_version = 1` and producer `formatVersion: 1` are independent versions. The service version covers registrations, durable receipts, errors and read responses. Unsupported versions fail explicitly; no version guessing or silent event rewriting.

## Domain and registration

IDs/text follow the event contract's 1–128 ASCII ID and 1–500 Unicode-code-point plain-text rules. Registration/tool schemas reject unknown fields, wrong types and null required IDs. The raw event boundary additionally rejects duplicate JSON keys, invalid UTF-8 and non-finite numbers, with booleans rejected where a number/version is expected. Render text literally. Registered records are immutable in this slice:

```json
{"projectId":"demo:project","name":"Synthetic project"}
{"sessionId":"demo:session","projectId":"demo:project","taskId":"demo:task","title":"Synthetic task journey"}
```

A project has zero or more sessions; each session has exactly one existing project and one task. Separate `sessionId` and `taskId` are caller supplied and compared by their own field, never inferred or required equal. **One task belongs to exactly one registered session in this ledger**, enforced by a unique task binding; a session covers the whole task journey, across reporters, delegations, runs, attempts and delivery retries. This bounded 1:1 session/task mapping prevents the same task's source history from splitting across sessions while retaining distinct identifiers for future evolution. A retry/resumed execution uses the original session and task, with appropriate run/attempt IDs. A genuinely different task needs both new identities. Session IDs never derive from a browser tab, day, MCP connection, RPC request ID or a protocol session header.

Registration compares all declared fields structurally. Equal ID/content is idempotent; same ID/different content, task already bound elsewhere, or attempted reparenting returns `registration_conflict`. Unknown project returns `project_not_found`. A successful new record gets server-owned `registeredAt` and `registrationReceiptId`; duplicate registration returns the first metadata unchanged. Project and session registration are separate atomic transactions. If project registration succeeded and session registration failed, the project remains; no implicit project rollback is claimed. There are no edit/delete/rename tools. IDs are unique within their entity kind; event IDs retain ledger-wide uniqueness.

Raw v1 envelopes remain valid reporting input without an application file workspace. Explicitly register their actual task ID and session binding before reporting them to durable storage through MCP. Input containing several tasks must be partitioned by exact task ID for explicit session submissions; never drop or reassign events implicitly. Event JSON gains no project/session fields. Export/backup retains the companion registration mapping; an event-only v1 export cannot convey project/session identity.

## Shared application core

DAM-37 owns a Python `Ledger` facade (implementation module `agent_work_ledger.ledger`), including database ownership and lifecycle. Public constructor:

```python
Ledger(data_dir, *, now=None, receipt_id=None, fault=None)
```

`data_dir` is a filesystem path (`str` or `os.PathLike`) resolved to the canonical private data directory; the database is its fixed `ledger.sqlite3`. `now` is an optional zero-argument callable returning a valid contract UTC timestamp; `receipt_id` is an optional zero-argument callable returning a valid server receipt ID. Defaults use the UTC clock and random UUIDs. No client can supply receipt metadata through an operation. `fault` is an optional test-only callable taking exactly `"before_commit"` or `"after_commit"`, invoked for an append transaction containing new events immediately before commit or after durable commit but before returning its receipt. Default is no hook. Tests may raise/terminate the worker there: before-commit failure rolls back, after-commit failure preserves the committed history for retry. This seam is never exposed through MCP, HTTP, configuration or the production CLI.

The constructor itself acquires exclusive lifetime ownership for that canonical database **before** opening/initializing/validating storage, and returns only after startup validation succeeds. Lock acquisition and release belong entirely to DAM-37; there is no prerequisite ASGI/service lock. A second `Ledger` instance in the same or another process targeting that database fails with `LedgerError(code="busy", ...)` and an actionable already-owned message, without modifying the database. Startup failure closes partial resources and releases acquired ownership. Corrupt/unreadable storage uses `storage_unavailable`, unknown storage version uses `unsupported_version` with field `storageVersion`; both preserve the file and supply recovery guidance. OS-backed process ownership must release on process exit/crash; stale sentinel-file existence alone is not an ownership lock.

`Ledger` implements `__enter__` returning the already-open instance, `__exit__` calling `close()` without suppressing the caller's exception, and public idempotent `close()` returning `None`. `close()` rolls back any uncommitted transaction, closes the connection and releases lifetime ownership, even on cleanup failure; previously committed history survives. Operations on a closed instance raise `LedgerError(code="storage_unavailable", ...)` with reopen guidance. Reopening is a new constructor call. DAM-37 independent QA can therefore run two ordinary Python worker processes using only `with Ledger(data_dir) as ledger: ...`, hold the first owner, observe the second rejection, then close/crash the first and verify a fresh owner opens the unchanged history. No DAM-38 application is needed for that gate.

The operation methods below return the versioned success result or raise `LedgerError` with the error fields below. Constructor/lifecycle calls return an instance/None, not an operation-result envelope; their errors use the same bounded fields for callers to report.

| Method | Input | Success `data` |
| --- | --- | --- |
| `register_project(projectId, name)` | Explicit ID and name | `{project, duplicate}`; project includes input plus first `registeredAt,registrationReceiptId` |
| `register_session(sessionId, projectId, taskId, title)` | Exact explicit binding | `{session, duplicate}`; session includes input plus first `registeredAt,registrationReceiptId` |
| `append_events(sessionId, envelopeJson, channel="mcp")` | Raw JSON text, or `append_bytes(sessionId, rawBytes, channel="mcp")` for strict byte boundary | `{receiptId,acceptedEventIds,duplicateEventIds}` after commit |
| `snapshot()` | No filter | `{formatVersion:1,projects,sessions,events,receipts}` read in one consistent transaction |

Every success is `{serviceVersion:1,ok:true,data:{...}}`. Every failure is `{serviceVersion:1,ok:false,error:{code,message,eventIndex,field,eventId}}`; three location/identity fields are always present and nullable. Messages are bounded remediation text, never raw content. A transport adapter translates `LedgerError` once; business validation/equality/storage is not reimplemented in MCP or UI.

`append_events` requires an existing session. Every event's `taskId` must equal its registered task; mixed/wrong task batches return `session_task_mismatch` and write nothing. Validate complete raw envelope and all events before conflict/receipt mutation. Preserve v1 strict parser depth guard 64, 1,048,576 UTF-8 bytes including whitespace and 1,000 event occurrences per submission, including duplicates. JSON object order/whitespace do not change equality. Compare every parsed producer field; no trimming, null normalization or receipt inclusion. Preserve JSON-escaped Unicode, including lone surrogate code units accepted by the current v1 browser parser; serialize them with ASCII escapes rather than failing Python UTF-8 encoding or inventing replacement characters. Include paired/lone surrogate and non-BMP parity fixtures. This preserves the existing event contract rather than adding a new Unicode rejection rule. Check incoming duplicates against each other and stored history. Accepted IDs are unique new IDs in incoming first-appearance order; duplicate IDs include every equal repeated occurrence. Counts can be obtained from these arrays. A batch conflict anywhere rejects the whole batch, with no new event receipts.

Server-generated registrationReceiptId and receiptId are opaque nonempty ASCII strings of at most 128 characters (production UUIDs suffice). They are not event identity. Event receipts are exactly `{eventId,receivedAt,receiptId,channel:"mcp"}`. The batch response receiptId is opaque; for new events it may also be their first receiptId. All new events in a batch share one valid UTC receivedAt. Equal repeats retain their first event receipt unchanged forever, including time and channel; an entirely duplicate batch allocates no event receipts. A retry may return a different batch response ID. Receipt and RPC IDs are not work attempts. Rejected requests create no event receipts. Commit is durable before returning success. Producer reports remain assertions; receipt proves storage acceptance only.

`snapshot()` includes **all** durable accepted events, not just the selected task, so existing graph cross-task binding diagnostics still have their source context. Events/paired receipts use canonical occurrence/event-ID order from v1; projects sort by projectId, sessions by sessionId (ASCII). Metadata and events/receipts are one consistent read, never a merge of separate racing reads. Unknown references and cycles remain accepted evidence diagnostics.

Bound the initial single-owner ledger to 1,000 projects, 1,000 sessions, 10,000 unique events and 8 MiB stored UTF-8 event JSON (serialize accepted objects once as compact JSON with ASCII escapes; count those stored UTF-8 bytes). New writes beyond a limit fail `storage_limit` atomically; all-duplicate retries and reads still succeed. This is an explicit local trial capacity, not a production scaling claim. Service read response is bounded to 32 MiB; malformed/oversized snapshot fails visibly rather than truncating a graph. No paging/live streaming/day grouping is promised in DAM-32. Future scale changes must preserve coherent graph/source semantics.

## Errors and transport mapping

Registration and append are **MCP-only operations**. A valid tool invocation that reaches the core returns its domain failure as a normal successful MCP protocol response (HTTP 200 in the selected JSON response mode), with `isError: true` and the versioned `ok:false` structured/text envelope. A domain conflict is not an HTTP 409, and a missing registered entity is not an HTTP 404. Do not map domain error codes to the MCP HTTP status. The same rule applies to core busy/storage errors reached during a tool call. SDK-level malformed request/unknown method/tool/invalid arguments remain protocol errors before domain dispatch.

| Core code | Domain condition / remedy |
| --- | --- |
| `invalid_input`, `invalid_utf8`, `leading_bom`, `invalid_json`, `duplicate_key`, `invalid_schema` | Correct raw text/bytes or named field |
| `unsupported_version` | Unsupported producer version in an append; use documented version |
| `input_limit`, `event_limit`, `storage_limit` | Split valid input or use supported ledger capacity; no partial writes |
| `event_id_conflict` | Keep old event; changed report needs new eventId |
| `registration_conflict`, `session_task_mismatch` | Reuse original binding or choose genuinely new identities; never overwrite |
| `project_not_found`, `session_not_found` | Explicitly register the missing entity first |
| `busy`, `storage_unavailable`, `receipt_error` | Preserve input IDs/content, correct environment and retry |

Actual HTTP boundaries are separate:

| Boundary | HTTP status / payload |
| --- | --- |
| `GET /v1/snapshot` or `GET /v1/health` without application authentication, available core | 200 and the documented `ok:true` read envelope |
| Read route cannot obtain valid storage/snapshot (`busy` or `storage_unavailable`) | 503 and versioned `ok:false` error envelope; never partial/empty success |
| Invalid/duplicate Host or present Origin on any HTTP route, including root/assets, reads and `/mcp` | 403 before dispatch; malformed HTTP rejected natively by the HTTP parser before ASGI (duplicate Host:400); no mutation |
| Outer `/mcp` body exceeds request bound | 413 before tool/core dispatch; separate from inner-envelope `input_limit` tool error |
| Unknown HTTP route / unsupported method | 404 / 405; no invented registration or append HTTP endpoint |

Storage constructor/version/corruption errors prevent readiness/startup rather than producing a fictitious HTTP write response. Only the existing read routes can produce the read failures above; registration/append-specific errors have no HTTP read-status mapping.

No response/network loss means **unconfirmed**, never accepted or failed work. Retry identical event IDs/content. Before-commit interruption leaves the prior state; after-commit/before-response interruption is recovered by idempotent retry. Unsupported/corrupt storage fails startup with recovery guidance and leaves files intact; this is not an empty successful ledger. Startup process-ownership errors are explicit, not an HTTP success.

## Storage and safe hydration

One DAM-37 Ledger instance holds exclusive lifetime process ownership of the chosen SQLite database from construction through close/crash (including startup validation); the service consumes that lifecycle, and a second owner fails clearly. Serialize transactions with bounded busy wait (5 seconds maximum) and explicit rollback. Use SQLite local files on a local filesystem, foreign keys enabled, synchronous FULL; transaction commit before acknowledgement. No network filesystems/multi-worker DB guarantees. WAL is optional only with explicit backup/checkpoint recovery and process crash tests. Data directory permission 0700; database/backup permissions 0600. Startup rejects unknown storage versions or failed integrity/binding/receipt consistency checks, never deletes/recreates the file. This local-defaults correction preserves existing version 1 data without migration; future schema upgrades must add tested migration/backup handling rather than reinterpret version 1. Stop the dedicated service before copying database backups (or use SQLite's consistent backup API); never copy a live DB file alone with an unaccounted WAL. Recovery creates a separate checked copy, preserving the failed original.

DAM-38 adds one documented browser export `acceptDurableSnapshot(rawBytes)` in `web/import/durable.js`. Input is the raw `/v1/snapshot` JSON response; success `{ok:true,snapshot,projects,sessions}`, error `{ok:false,error}` without snapshot. Validate service version/schema, raw UTF-8/duplicate-key/size/depth controls, complete v1 event shapes, unique event IDs, registration ID/binding uniqueness, each event's exact registered task binding, and one-to-one receipt correspondence (no missing/duplicate/extra receipt), valid UTC timestamps/nonempty opaque IDs and known `mcp` channel. Validate counts/limits before publishing anything. Freeze nested producer/receipt/registration objects; canonicalize ordering. Return a snapshot accepted by existing `projectTask/taskIds/timeline` APIs without generating receipts or calling the file-import receipt path. Importer internal helpers may be shared; the existing raw file API/fixtures remain unchanged. Adapter failure leaves prior application snapshot and graph/source selection intact. Validate the entire global source map before selected-session projection; never trust server JSON through an unchecked cast.

The UI displays exact accepted parsed producer JSON separately from original durable receipts, keeping configured versus reported-tool-verification versus unknown distinct. Existing projection diagnostics retain every named source, including cross-task conflict evidence. A single event source matches its original receipt after refresh, restart and retry. Dates shown as registration/receipt metadata do not imply project/day grouping or producer occurrence dates.
